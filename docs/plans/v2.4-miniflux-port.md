Authored by the planner agent. This plan is the ONLY output of the planning
pass; an executor implements it and a reviewer audits the diff against it.

Merge commit `96541fb` resolved `DankRssWidget.qml` /
`DankRssWidgetSettings.qml` to the independent v2 rewrite's versions. PR #3
(`830ff8e`) and PR #6 (`48a1313`) are merged into git history, credited in

  `sourceMode` is exclusive, exactly as PR #6 designed it.

// niri overview is open -- otherwise clicking a thumbnail in the overview
// to switch workspaces can land on this widget instead and silently open
// a link / mark an item read. A plain "inOverview" check is not enough:

        && typeof NiriService !== "undefined"
        && CompositorService.isNiri)

    function onInOverviewChanged() {
        if (NiriService.inOverview)
            root._overviewGuard = true;

    interval: 450
    onTriggered: root._overviewGuard = false
}

## 2. Task B — Miniflux source mode

### 2.1 Item identity (decision #1)

Miniflux entries have a numeric `entry.id`. Map it to the frozen Item
`id` field with a **new, distinct prefix `"m:"`** so it can never collide
with `"g:"` (guid/atom-id), `"l:"` (link), or `"h:"` (hash fallback) from
`makeItemId`. Concretely: `id: "m:" + String(entry.id)`.

This is produced by a new pure function in `FeedParser.js`,
`parseMinifluxEntries(json)` (see §2.4), NOT inline in the QML — it is a
pure JSON-to-Item mapping, exactly the kind of logic `FeedParser.js` already
owns for RSS/Atom, and it must be unit-testable the same way.

### 2.2 Read state (decision #2)

PR #6's `entryStatusMap` (`{ entryId: { status, starred } }`) is DELETED.
Miniflux read state collapses onto the existing `readMap`/`readOrder`
(keyed by the `"m:"+id` stable id) — the same structures RSS items already
use. Miniflux becomes a **sync target**, not a separate source of truth:

- **Local action is immediate and authoritative for the UI**: clicking a row
  or the mark-read button calls the existing `root.markRead(itemId)` /
  `root.markUnread(itemId)` exactly as today (updates `readMap`, persists,
  no behavior fork). If `sourceMode === "miniflux"` AND (marking read AND
  `root.syncReadOnOpen`, OR explicitly toggling read/unread via the
  mark-read button), ALSO push the change to the server:
  `minifluxMarkRead([numericId])` / `minifluxMarkUnread([numericId])`,
  fire-and-forget with a toast on failure (matching PR #6's
  `toastError` pattern). The local state is not rolled back on a failed
  push — a transient network failure must not un-mark something the user
  just read; the next fetch's reconciliation (below) will correct drift.
- **Server state wins on fetch reconciliation**: every successful Miniflux
  fetch reconciles each entry's server `status` into `readMap`/`readOrder`
  — an entry the server says is `"read"` gets `markRead(id)` called (if not
  already read locally), and one the server says is `"unread"` gets
  `markUnread(id)` called (if locally marked read). This makes the server
  the eventual source of truth after every refresh, while still giving
  instant local feedback between refreshes.
- Numeric-id extraction for the API calls: strip the `"m:"` prefix
  (`itemId.slice(2)`) before passing to `minifluxMarkRead`/`minifluxMarkUnread`.

### 2.3 Bookmarks vs starred (decision #3)

Unify: the existing `bookmarkMap`/`bookmarkOrder`/`toggleBookmark()` is
reused as-is for Miniflux's starred state — no separate starred map. In
Miniflux mode, `root.toggleBookmark(itemId)` additionally calls
`minifluxToggleStar(numericId)` (PR #6's `PUT /v1/entries/{id}/bookmark`,
which toggles server-side with no body). Reconciliation on fetch: each
entry's server `starred` boolean is merged into `bookmarkMap` the same way
read status is (add to `bookmarkOrder` if server says starred and not
locally bookmarked; remove if server says not-starred and locally
bookmarked).

**Bookmarks made while in RSS mode**: they are untouched. `bookmarkMap` is
not source-mode-scoped — an RSS bookmark's id has an `"h:"`/`"g:"`/`"l:"`
prefix that can never collide with a Miniflux `"m:"` id, so switching
`sourceMode` naturally hides RSS bookmarks from view (their items aren't in
`allItems` while in Miniflux mode) without deleting them; switching back to
RSS mode restores them exactly as left. This is a natural consequence of
`filterMode === "bookmarked"` filtering `root.allItems`, which is fully
replaced per source mode — no special-casing needed, but call it out in
code comments so a future reader doesn't "fix" it into being scoped.

### 2.4 Fetching (decision #4)

**One synthetic feed status entry**, not per-category — Miniflux has no
concept of the widget's per-feed list; it presents one logical stream
(unread or starred entries across all subscribed feeds). Reuse the EXACT
same `feedStatuses` array / `CONTRACT 6` shape with a single synthetic
entry, e.g. `{ url: root.minifluxUrl, name: "Miniflux", state, lastFetched,
lastSuccess, lastError, itemCount }`, so the settings panel's existing
per-feed-status rendering code needs no fork — it just renders a
one-element list. (If the settings panel currently assumes `feeds` and
`feedStatuses` are url-keyed and parallel, this one entry must use
`root.minifluxUrl` as its `url` key so `statusForUrl` still resolves it if
reused — see §2.6.)

**Generation guard**: `fetchAllFeeds()` branches at the top:

```js
function fetchAllFeeds() {
    if (!root.isRunnable())
        return;
    root.loadReaderState();
    root.fetchGeneration++;
    var gen = root.fetchGeneration;

    if (root.sourceMode === "miniflux") {
        root.fetchMinifluxEntries(gen);
        return;
    }
    // ... existing RSS branch, using the same `gen` already incremented above
}
```

`fetchMinifluxEntries(gen)` must check `gen !== root.fetchGeneration` in its
Proc callback and return early, exactly like `fetchFeed`'s stale-callback
guard — this is the fix for the exact class of bug CONTRACT 7 fixed for RSS,
which PR #6 (predating CONTRACT 7) never had.

**Proc id**: use `Proc.runCommand(null, [...], callback)` — a null id,
matching the rewrite's `fetchFeed` (see the `T4` comment at line ~433) —
NOT PR #6's `"miniflux:" + root.procTag + ":" + callId` fixed-string ids.
Fixed ids sharing a debounce-map key across overlapping calls have exactly
the clobbering bug T4 already fixed once for RSS; do not reintroduce it for
Miniflux. Since `Proc.runCommand(null, ...)` self-cleans, the `procTag`
property from PR #6 is not needed at all in the ported version — drop it.

**`classifyFetch` still applies**: reuse `ReaderState.classifyFetch(exitCode,
output, items.length)` for the synthetic status exactly as `fetchFeed` does,
after JSON-parsing (a JSON parse failure should be treated like RSS's
`parseFailed` — set `status.lastError = "Parse failed"` and pass
`items.length === 0` into `classifyFetch` so it still resolves to `"error"`).

**Curl hardening (decision #4, security)**: PR #6's `minifluxApiCall` used:

```js
["curl", "-sS", "--connect-timeout", "5", "--max-time", "25",
 "-X", method, "-H", "X-Auth-Token: " + root.minifluxToken, ...]
```

This predates the RSS hardening flags. Add the SAME flags the RSS fetch
uses in the ported version, for every Miniflux curl invocation (fetch
entries, mark read/unread, toggle star, test-connection, feed list):

```
"--proto", "=http,https",
"--proto-redir", "=http,https",
"--max-redirs", "5",
"--max-filesize", "5000000"
```

Apply the same post-download length re-check (`output.length > 5000000`)
before `JSON.parse` that `fetchFeed` applies before `FeedParser.parseFeed`.

### 2.5 The API token (decision #5)

No storage-mechanism change this pass — it stays in plaintext plugin
settings (`pluginData.minifluxToken`), consistent with the rest of the
plugin. Requirements for the port:

- **Never logged**: no `console.log`/`console.warn` may include
  `root.minifluxToken` or a constructed `args` array that contains it, even
  in an error path. Grep the diff for `minifluxToken` next to any
  `console.*` call before calling this done.
- **Never in a toast**: `toastError()` messages must describe the failure
  ("Miniflux fetch failed", "Connection failed: check URL and token") and
  must never interpolate the token or the full authenticated URL.
- **Never shell-interpolated**: PR #6 already did this correctly —
  `Proc.runCommand` is always called with an argv array, and the token is
  passed as its own array element (`"-H", "X-Auth-Token: " + token`), never
  concatenated into a single string handed to `sh -c`. **Verified via `git
  show 48a1313`: no call site in PR #6 uses `sh -c`, `bash -c`, or string
  concatenation into a single Proc arg.** The port must preserve this
  exact pattern (separate argv elements) in every new call site added.

### 2.7 Search, filters, selection (decision #7)

These operate purely on `root.allItems` (via `ReaderState.filterItems`,
`ReaderState.tokenizeQuery`/`matchesTokens`) and `feedModel` — both of which
are populated identically regardless of source mode once
`parseMinifluxEntries()` produces standard Items. **No changes needed** to
`applyFilter()`, the search field, the filter chips, or the selection model
(`selectedMap`, `toggleSelected`, `bulkMarkReadSelected`, `bulkSaveSelected`,
`clearSelection`) — they already only look at `item.id`/`item.title`/
`item.description`/`item.source` and the read/bookmark maps, all of which
Miniflux items populate correctly via `parseMinifluxEntries`.

One integration point DOES need adapting: `bulkMarkReadSelected()` and
`setAllRead()` currently only touch local `readMap`/`readOrder`. In Miniflux
mode, extend both to also push to the server for every id being changed
(strip `"m:"` prefix, batch into one `minifluxMarkRead`/`minifluxMarkUnread`
call per bulk action rather than one call per id — Miniflux's `PUT
/v1/entries` already accepts an array of `entry_ids`). Filter the id list to
only Miniflux ids (`id.indexOf("m:") === 0`) before calling the API — a
mixed-mode id list should never occur in practice (only one source mode's
items are ever in `allItems` at a time) but the filter is a cheap
correctness guard against future drift. `bulkSaveSelected()` similarly
should call `minifluxToggleStar` for each id — but ONLY if not already
starred (since the endpoint toggles, not sets); check `bookmarkMap` before
calling to avoid accidentally un-starring an already-starred entry the
bulk-save selected alongside new ones.

## 4. FeedParser.js / ReaderState.js changes

### 4.1 `FeedParser.js`: `parseMinifluxEntries`

New exported function (add to the `module.exports` block):

```
parseMinifluxEntries(json, defaultSourceUrl) -> Item[]
```

- `json` is the ALREADY-`JSON.parse`d response body from
  `GET /v1/entries` (an object with an `entries` array — see PR #6's
  `data.entries || []`). Passing the parsed object (not a JSON string)
  keeps this consistent with how `parseFeed` takes already-decoded XML
  text; if the executor prefers passing the raw string and parsing inside
  the function (to also unit-test malformed-JSON handling per §4.3), that
  is acceptable — pick one and document it in a comment, but the malformed/
  empty test cases in §4.3 assume the function itself does the
  `JSON.parse` and never throws.
- `defaultSourceUrl` is `root.minifluxUrl`, used to fill `sourceUrl` on each
  Item (Miniflux entries don't carry the widget's configured feed URL,
  only their own per-entry `feed` object).

**Field-by-field mapping**, derived from PR #6's `fetchMinifluxEntries`
(`git show 48a1313`, the `items.push({...})` block):

| Item field    | Miniflux JSON field(s) used | Notes |
|---|---|---|
| `id`          | `entry.id` | `"m:" + String(entry.id)` — decision #1 |
| `title`       | `entry.title` | falls back to `""` |
| `link`        | `entry.url` | |
| `description` | `entry.content` then `entry.summary` | `cleanText(stripHtml(...))`, same as PR #6 |
| `timestamp`   | `entry.published_at` | `new Date(entry.published_at).getTime() \|\| 0` |
| `dateStr`     | `entry.published_at` | raw string, per CONTRACT 2 |
| `source`      | `entry.feed.title` | `entry.feed ? entry.feed.title : ""` |
| `sourceUrl`   | not present per-entry in PR #6 | use `defaultSourceUrl` (the configured Miniflux server URL) |
| `imageUrl`    | `entry.enclosures[].url` where `.mime_type` starts with `"image/"`, else fall back to an `<img>` extracted from `entry.content`/`entry.summary` | this is PR #6's `minifluxEntryImage` — port its body into this function, calling the EXISTING `extractImageUrl(block, content)` for the content-fallback path with `block=""` (no XML block to scan for `media:`/`enclosure` tags — Miniflux already gave us `entry.enclosures` directly) |

Additionally, since read/bookmark reconciliation needs server status per
entry (§2.2/§4.2), `parseMinifluxEntries` should ALSO return, alongside (or
attachable to) each Item, the raw `entry.status` ("read"/"unread") and
`entry.starred` (bool) — the executor's choice of shape: either (a) return
`{ items: Item[], serverStatus: [{id, status, starred}] }` instead of a
bare array (requires a doc-comment noting this deviates from `parseFeed`'s
plain-array return), or (b) return items only and have the QML side
separately walk the ALREADY-PARSED entries object it holds onto for
reconciliation. **Recommend (a)** for testability — reconciliation logic
belongs in pure, tested code, not inline QML — with the return shape
documented at the top of the function.

Malformed input handling (§4.3 has the exact test cases):
- `json` is not an object / has no `entries` array -> return the empty
  shape (`{ items: [], serverStatus: [] }` or equivalent), never throw.
- An individual entry missing `id` -> skip it (an id-less Miniflux entry
  cannot be stably tracked; log nothing, silently drop, mirroring how
  `parseRssFeed`/`parseAtomFeed` skip items with neither title nor link).
- `entry.published_at` unparseable -> `timestamp: 0`, `dateStr` still the
  raw (unparseable) string, matching existing RSS/Atom behavior for bad
  dates.

### 4.2 `ReaderState.js`: `reconcileServerStatus`

```
reconcileServerStatus(readOrder, bookmarkOrder, serverEntries, cap) ->
    { readOrder, bookmarkOrder, readChanged, bookmarkChanged }
```

- `serverEntries` is `[{ id, status, starred }]` where `id` is the
  ALREADY-PREFIXED `"m:"+entryId` string (caller's job to prefix before
  calling this — keeps this function decoupled from `FeedParser`'s prefix
  choice, consistent with how the rest of `ReaderState.js` never
  constructs ids, only consumes them).
- For each entry: if `status === "read"` and the id is not in
  `boundIdList(readOrder)`'s membership, add it via the same
  prepend-dedupe-cap logic `addRead` uses (delegate to `addRead` in a
  loop, or build the incoming list and call `addAllRead` once — prefer
  `addAllRead(readOrder, idsToMarkRead, cap)` for one bulk op instead of N
  calls). If `status === "unread"` and the id IS currently read, remove it
  (delegate to `removeRead` per id, or build a drop set and filter once).
- Same pattern for `starred` vs `bookmarkOrder`/`isBookmarked`, delegating
  to `addAllBookmarked` / a bulk removal.
- Pure function, no I/O, no Qt — same constraints as the rest of the file.
- Server wins unconditionally in this function — it is called ONLY at
  fetch time, after the widget's own immediate local pushes have already
  had a chance to reach the server (the "local action wins immediately"
  half of decision #2 is enforced by NOT calling this function except
  right after a fresh fetch, not by any conflict logic inside it).

### 4.3 Test cases the executor must add

`tests/feed-parser.test.js` — `describe("parseMinifluxEntries", ...)`:
1. Parses a well-formed `{ entries: [...] }` object into Items with `"m:"`-
   prefixed ids matching `entry.id`.
2. `id` collision safety: an RSS `makeItemId` output for some `guid` and a
   Miniflux entry with the SAME numeric-looking id never produce equal
   strings (e.g. assert `parseMinifluxEntries({entries:[{id:42,...}]}).items[0].id
   !== makeItemId("42", "", "src", "t", "")`).
3. `title`/`link`/`description` map correctly; `content` preferred over
   `summary` when both present; HTML is stripped from `description`.

## 5. Risks — what could break existing RSS-mode behavior

This is the highest-risk category since RSS mode is what the user actually
uses today. Concrete failure modes to guard against, and how the plan
already addresses each:

1. **`fetchAllFeeds()` branch ordering**: `root.fetchGeneration++` MUST
   happen before the `sourceMode` branch, not after, or the Miniflux path
   and RSS path could get out of sync on generation numbering if
   `sourceMode` is ever toggled mid-flight. §2.4's snippet shows the
   correct order — the executor must not reorder it.
2. **Shared properties reused across modes**: `readMap`, `bookmarkMap`,
   `allItems`, `feedModel`, `selectedMap` are ALL shared, unscoped by
   `sourceMode`. A bug in Miniflux-mode item construction (e.g. a missing
   `id`) could silently corrupt `readMap` in a way that also shows up after
   switching back to RSS mode, IF an RSS item ever happened to produce the
   same id string — decision #1's `"m:"` prefix is the load-bearing
   mitigation here; if the executor ever writes a Miniflux id WITHOUT the
   prefix (e.g. a shortcut in the reconciliation path that uses the raw
   numeric id instead of `"m:"+id`), read-state corruption across modes
   becomes possible. Explicitly test for this (test #2 in §4.3).
3. **`onSourceModeChanged` must not exist as a bare handler that clobbers
   more than intended.** PR #6 cleared `feedModel`, `entryStatusMap`, and
   `readLinks` on mode switch. The ported version must NOT clear
   `readMap`/`bookmarkMap` (those are cross-mode-safe now, per #2 above) —
   only `feedModel.clear()` and `root.allItems = []` should happen on a
   mode switch, then `fetchAllFeeds()`. Clearing `readMap` on every mode
   toggle would be a regression (it would un-read everything the user has
   read, in BOTH modes, every time they flip the settings toggle).
4. **`timer` (the periodic refresh Timer) is mode-agnostic today and must
   stay that way** — do not add a second timer for Miniflux; reuse the
   existing `timer`/`updateInterval` exactly as RSS does, since
   `fetchAllFeeds()` already branches internally.
5. **Settings panel changes must not shift any existing `visible:` bindings
   for standard-mode sections in a way that breaks when `sourceMode` is
   undefined/missing** (a user upgrading from a version before this port
   has no `sourceMode` key at all) — `property string sourceMode:
   pluginData.sourceMode ?? "standard"` must default existing installs into
   standard/RSS mode with ALL current behavior intact and every
   RSS-management UI section still visible. Verify this explicitly (§7).
6. **Proc id collisions reintroduced via the settings-panel calls** (Test
   Connection, Force Refresh, feed-list fetch) — PR #6 used fixed string
   ids there too. Lower risk than the main widget (settings panel isn't
   background-timer-driven) but a user mashing "Test Connection" twice
   before the first returns would still clobber the callback under PR #6's
   original fixed-id scheme. Use `null` ids there too per §2.6.
7. **`finalizeFetch` sort/cap logic must not gain a Miniflux special case**
   — Miniflux items feed into the EXACT same `finalizeFetch(items)` (or
   `ctx`-based `finalizeFetch`, matching the current rewrite's signature)
   that RSS uses, sorting/capping/notifying identically. If the executor is
   tempted to skip sorting because Miniflux already returns entries
   `order=published_at&direction=desc`, resist it — `sortMode` (oldest/
   byFeed) is a user setting that must still apply in Miniflux mode, and
   `byFeed`'s `maxPerFeed` grouping over `entry.feed.title` is a reasonable,
   free feature to inherit rather than special-case away.
8. **Curl hardening flags added to Miniflux calls must not be added
   incorrectly to the RSS calls** — they already have them; a careless
   find-and-replace across the file could duplicate flags on the RSS
   `fetchFeed` args array. Diff-review this specifically.
