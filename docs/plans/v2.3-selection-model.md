# RSS Widget v2.3 — Selection Model + Bulk Actions

Authored by the planner agent. Builds on v2.2 (`docs/plans/v2.2-ui-fixes.md`),
whose fixes are already live in `DankRssWidget.qml`: MouseArea-declared-first
+ margin-carve-out, `HoverHandler` for hover state, `Layout.*` sizing in the
action row, always-`enabled: true` controls at idle opacity ~0.45/1.0. This
plan does not touch or undo any of that — it extends the same patterns.

## 1. Scope + non-goals

**Scope:**
- Repurpose the existing leading-position-less checkbox as a **transient,
  in-memory selection** control, moved to the row's **leading** edge.
- Add a **third**, trailing "mark read" toggle button (the read-state
  control the checkbox used to be).
- Add a **contextual selection bar** that replaces the filter/mark-all row
  when `selectedCount > 0`, with Save / Mark read / Clear bulk actions.
- Add pure selection helpers to `ReaderState.js` with tests.

**Non-goals:**
- No persistence of selection across restarts or refreshes beyond the
  in-memory session (S1). Nothing new is written via `writeState`.
- No change to read/bookmark persistence shape, id precedence, or
  `docs/plans/v2-contract.md`.
- No redesign of settings, feed list model, or the empty/loading states.
- No new widget min dimensions.
- No QML execution in this repo (no `qml`/`qs`/`quickshell` binary) — QML
  changes are review + live-verified only, same constraint as v2.2.

## 3. Delegate restructure

### Child declaration order (top to bottom, as written in the file)

1. `HoverHandler { id: rowHover }` — unchanged from v2.2.
2. `MouseArea { id: itemMouseArea }` — unchanged position (first, before
   `itemColumn`), but now carves out **both** edges.
3. `RowLayout { id: itemColumn }` containing, in order:
   1. **NEW: leading selection checkbox** (`DankActionButton`)
   2. `ColumnLayout` (text content) — unchanged internally
   3. Thumbnail `Rectangle` — unchanged
   4. **NEW: trailing mark-read `DankActionButton`** (was the checkbox in
      v2.2; same behavior, new position/icon)
   5. Trailing bookmark `DankActionButton` — unchanged

Declaring the selection checkbox as `itemColumn`'s first child, before the
text `ColumnLayout`, is what pushes the text over automatically — the
`ColumnLayout`'s `Layout.fillWidth: true` just claims whatever width is
left in the `RowLayout` after the leading checkbox, thumbnail, and two
trailing buttons take their preferred widths. No manual width math is
needed on the text column itself; this is the same mechanism that already
makes room for the two trailing buttons today.

### Margin arithmetic (both `viewMode` values)

Reuse the existing `controlSize` (22) and `controlsRowWidth` contract, and
add a symmetric leading-side constant:

```qml
readonly property int controlSize: 22
// Gap between the leading checkbox and the text column, and between the
// two trailing buttons — both equal itemColumn.spacing, which is a FIXED
// Theme.spacingS regardless of viewMode (only itemColumn's outer
// anchors.margins vary by viewMode, not its internal spacing).
readonly property int leadingControlWidth: controlSize + Theme.spacingS
readonly property int controlsRowWidth: controlSize * 2 + Theme.spacingS
```

```qml
MouseArea {
    id: itemMouseArea
    anchors.fill: parent
    anchors.leftMargin: (root.viewMode === "compact" ? Theme.spacingXS : Theme.spacingS)
        + itemDelegate.leadingControlWidth
    anchors.rightMargin: (root.viewMode === "compact" ? Theme.spacingXS : Theme.spacingS)
        + itemDelegate.controlsRowWidth
    ...
}
```

Worked out for both modes (outer margin is the only term that changes):

| viewMode | leftMargin | rightMargin |
|---|---|---|
| `"compact"` | `spacingXS + 22 + spacingS` | `spacingXS + 44 + spacingS` |
| `"expanded"` | `spacingS + 22 + spacingS` | `spacingS + 44 + spacingS` |

This is the same derived-from-real-control-sizes pattern DMS itself uses
in `/usr/share/quickshell/dms/Modules/DankDash/Overview/CalendarOverviewCard.qml:966-985`
(`anchors.leftMargin: taskItem.isLocalTask ? 32 : 6`,
`anchors.rightMargin: taskItem.canModify ? 64 : 0`) — except this plan
derives both numbers from `controlSize`/`Theme.spacingS` instead of
hardcoding them, consistent with v2.2's existing `controlsRowWidth` and
the "no magic numbers" instruction.

Neither margin depends on `viewMode` for its *control-width* term — only
the *outer* `Theme.spacingXS`/`Theme.spacingS` term changes, exactly
mirroring how `controlsRowWidth` already worked pre-this-plan. No separate
compact-mode code path is needed.

## 4. Contextual selection bar (S6)

**Swap mechanism: two sibling `RowLayout`s, `visible:` bindings — not a
`Loader`.**

Justification: both rows are lightweight (a handful of `Rectangle`/`Text`/
`DankActionButton` children, no async content, no images) — a `Loader`'s
create/destroy churn buys nothing here and adds `Loader.status`/
`sourceComponent` timing complexity for zero benefit. This file already
relies on exactly this pattern successfully: the search field is
`visible: root.searchActive && ...` (line 719) and Qt Quick Layouts
already excludes invisible children from layout (the same fact the v2.2
plan relied on for the thumbnail). Two `RowLayout`s as siblings inside the
parent `ColumnLayout`, visibility toggled on `root.selectedCount`, get
this collapse/expand behavior for free.

**Layout.\* sizing for every child:** the count `StyledText` is
`Layout.fillWidth: true` (absorbs remaining space, elides if the count
text somehow got long, which it never will — "N selected" is short); Save
and Mark-read mirror the existing mark-all `Rectangle` pattern exactly
(`Layout.preferredWidth` from `implicitWidth`, `Layout.minimumWidth` as an
icon-only floor); Clear is a bare `DankActionButton` with fixed
`Layout.preferredWidth/Height: 22` (never shrinks — it is the escape
hatch out of selection mode and must always be reachable).

**Narrow-width behavior:** Save/Mark-read labels drop at `widgetWidth <
300`, identical threshold to the existing mark-all label, for visual
consistency. Unlike the normal row's mark-all control (which can vanish
entirely below 160px), **Save/Mark-read/Clear are never fully hidden** —
this bar exists specifically to host these three actions, so hiding one
would strand the user mid-selection with no way to act on or clear it.
The floor is icon-only (3 × 22px + spacing + count text), same accepted
100px-floor limitation already flagged in v2.2 for the filter chips: at
the extreme minimum width this bar may be visually cramped, but nothing
disappears silently.

## 5. `ReaderState.js` — new functions and tests

**S9 decision: selection is a plain object map, NOT a `boundIdList`-style
array.** `boundIdList`'s cap/dedupe/newest-first-order machinery exists to
guard *persisted* state (corrupted state files, unbounded growth across
restarts). Selection is never persisted, is implicitly bounded by the
number of currently-visible items (itself capped by `maxItems`), and has
no ordering semantics — only membership matters. A map gives O(1)
toggle/lookup and mirrors the existing `readMap`/`bookmarkMap` shape
(built from a list via `buildIdMap`) that the QML layer already consumes
directly (e.g. `root.readMap[model.itemId]`). Reusing `boundIdList`/an
id-order list for selection would add cap/order bookkeeping the feature
does not need.

**S10 decision:** prune on every visible-set rebuild (`applyFilter()`),
keyed against the current `items` array, so `selectedCount` can never
exceed what's on screen. Selection for ids that remain visible survives a
refresh (map membership is untouched by pruning if the id is still
present); ids whose items disappeared are dropped from the map.

### New functions (add to `ReaderState.js`, export all five)

```js
// Selection is a plain { id: true } map — see S9 in v2.3 plan for why this
// is NOT a boundIdList array (no persistence, no cap, order irrelevant).

function toggleSelected(selectedMap, id) {
    if (typeof id !== "string" || id.length === 0) {
        return selectedMap || {};
    }
    var map = Object.assign({}, selectedMap || {});
    if (map[id]) {
        delete map[id];
    } else {
        map[id] = true;
    }
    return map;
}

function clearSelection() {
    return {};
}

function countSelected(selectedMap) {
    if (!selectedMap) return 0;
    return Object.keys(selectedMap).filter(function (k) { return selectedMap[k]; }).length;
}

// Drop any selected id whose item is no longer in `items` (S10) — keeps
// selectedCount from ever exceeding what's currently visible.
function pruneSelected(selectedMap, items) {
    if (!selectedMap) return {};
    var present = buildIdMap((items || []).map(function (i) { return i ? i.id : ""; }));
    var out = {};
    for (var k in selectedMap) {
        if (selectedMap[k] && present[k]) {
            out[k] = true;
        }
    }
    return out;
}

// Bulk-bookmark, additive only (S7) — mirrors addAllRead exactly (same
// generic "prepend + dedupe + cap" list operation), given a distinct name
// at the bookmark call sites so the code reads correctly there. Delegates
// to addAllRead rather than duplicating its body.
function addAllBookmarked(bookmarkOrder, ids, cap) {
    return addAllRead(bookmarkOrder, ids, cap);
}
```

### Required new tests — `tests/reader-state.test.js`

New `describe("selection", ...)` block:

```js
describe("selection", () => {
    test("toggleSelected adds an unselected id", () => {
        assert.deepStrictEqual(R.toggleSelected({}, "a"), { a: true });
    });

    test("toggleSelected removes a selected id", () => {
        assert.deepStrictEqual(R.toggleSelected({ a: true }, "a"), {});
    });

    test("toggleSelected ignores an empty/invalid id", () => {
        assert.deepStrictEqual(R.toggleSelected({ a: true }, ""), { a: true });
        assert.deepStrictEqual(R.toggleSelected({ a: true }, null), { a: true });
    });

    test("clearSelection always returns an empty map", () => {
        assert.deepStrictEqual(R.clearSelection(), {});
    });

    test("countSelected counts truthy keys only", () => {
        assert.strictEqual(R.countSelected({ a: true, b: true }), 2);
        assert.strictEqual(R.countSelected({}), 0);
        assert.strictEqual(R.countSelected(null), 0);
    });

    test("pruneSelected drops ids whose item is no longer present", () => {
        const items = [{ id: "a" }, { id: "c" }];
        const out = R.pruneSelected({ a: true, b: true, c: true }, items);
        assert.deepStrictEqual(out, { a: true, c: true });
    });

    test("pruneSelected on an empty item set clears everything", () => {
        assert.deepStrictEqual(R.pruneSelected({ a: true }, []), {});
    });

    test("pruneSelected handles an empty selection safely", () => {
        assert.deepStrictEqual(R.pruneSelected({}, [{ id: "a" }]), {});
        assert.deepStrictEqual(R.pruneSelected(null, [{ id: "a" }]), {});
    });
});

describe("addAllBookmarked", () => {
    test("adds all selected ids to the front, newest first", () => {
        assert.deepStrictEqual(R.addAllBookmarked(["old"], ["a", "b"]), ["a", "b", "old"]);
    });

    test("bulk save when some items are already bookmarked does not duplicate them", () => {
        const out = R.addAllBookmarked(["a", "old"], ["a", "b"]);
        assert.deepStrictEqual(out, ["a", "b", "old"]);
    });

    test("respects the cap", () => {
        assert.deepStrictEqual(R.addAllBookmarked(["c"], ["a", "b"], 2), ["a", "b"]);
    });

    test("empty ids list is a no-op beyond dedup/cap of the existing order", () => {
        assert.deepStrictEqual(R.addAllBookmarked(["x", "y"], []), ["x", "y"]);
    });
});
```

## 7. Risks

- **Row crowding at narrow widths with THREE controls + optional
  thumbnail:** the delegate now reserves `leadingControlWidth (22 + S)` on
  the left in addition to the existing `controlsRowWidth (44 + S)` on the
  right. At the widget's ~100px floor, in expanded mode with a thumbnail
  (48px) also present, the fixed chrome alone
  (`leftMargin + thumbnail + rightMargin` ≈ 22+S + 48 + 44+S, ignoring
  outer anchors.margins) can consume most or all of a 100px-wide row,
  leaving near-zero width for title text. This is a pre-existing
  trajectory (v2.2 already reserved the trailing 44px), but adding a third
  control's worth of leading space makes it materially worse. **Not
  addressed by this plan** — flagged as an accepted limitation, same
  posture as v2.2's 100px chip-clipping note. If unacceptable in live
  testing, a follow-up should consider auto-switching to compact mode (no
  thumbnail) below some width threshold, which is a design decision this
  plan does not make.
- **Selection-bar height/row identity:** using two sibling `RowLayout`s
  assumes both have essentially equal `implicitHeight` (both are 22px-tall
  control rows) so the swap doesn't visibly jump the list below it. Worth
  a live check, not just a review-time assumption.
- **`applyFilter()` prune placement:** this plan assumes `fetchAllFeeds()`
  (or whatever rebuilds `allItems` after a refresh) calls `applyFilter()`
  afterward already, so hooking the prune only into `applyFilter()` is
  sufficient for S10. If a refresh path exists that mutates `allItems`
  without ever calling `applyFilter()`, the prune would be skipped for
  that path — the executor should grep all `allItems =` assignment sites
  before finalizing and confirm each is followed (directly or via a
  property-change handler) by `applyFilter()`.

## Something I want to flag

**S4/DMS precedent (CalendarOverviewCard.qml:966-985) uses hardcoded
margin numbers (32/6, 64/0), not derived ones.** This plan intentionally
does NOT copy that hardcoding — it keeps deriving both margins from
`leadingControlWidth`/`controlsRowWidth` (as v2.2 already did for the
right side), because a magic-number margin would silently drift out of
sync if `controlSize` or `Theme.spacingS` ever changes. I'm noting this
because the frozen decision cites that file as precedent for *using both
margins*, which this plan follows, but not as precedent for *hardcoding*
the values, which this plan deliberately deviates from for maintainability.
